# Роли и права

Архитектура Prism строится на одном принципе: **скрыть от пользователя всю инфраструктурную сложность, а внутри обменять жёсткие границы на высокую автономность и отказоустойчивость.**

Пять плагинов (`dsh-concierge-ui`, `dsh-workspace-registry`, `dsh-orchestrator`, `dsh-mesh-node`, `dsh-im-gateway`) взаимодействуют через три строго изолированных уровня.

## Шесть принципов проектирования

1. **Zero-Workspace UX**: Веб-интерфейс и мессенджеры дают доступ к беседе. В веб-интерфейсе видны карточки задач, а доступная для чтения история открывается в рабочих областях DSH.
2. **Strict Isolation**: чем ближе агент к пользователю, тем строже его ограничения. **L1** полностью лишён инструментов работы с файлами и терминалом — это защищает от эскалации через инъекции и не засоряет контекст маршрутизации.
3. **Silent-by-Default Actor**: обычный текст L1 остаётся внутренним размышлением. Любой видимый ответ пользователю отправляется явно через `send_user`, а межуровневое взаимодействие идёт асинхронно через постоянные очереди.
4. **Self-Describing Routing**: каждый уровень задаёт собственный пул моделей с описанием возможностей (`description`) и переопределением промпта. L1 и L2 выбирают оптимальную модель на лету через `list_models`.
5. **Location Transparency**: `dsh-mesh-node` оборачивает удалённые узлы в стандартный Subagent Provider `prism-<nodeId>`. Поскольку L3 всегда наследует рабочую область L2, частые файловые операции остаются локальными на целевом узле.
6. **Virtual Facade & Copy-on-Conflict**: Каждый уровень работает в собственном сеансе DSH. При конфликте блокировки записи исполнитель создаёт новый сеанс и атомарно обновляет привязку. Для просмотра истории используются отдельные сеансы.

## Три уровня изоляции

| Роль | Рабочая область | Назначение и границы прав |
| --- | --- | --- |
| **L1** | Проект по умолчанию | Общается с пользователем, запрашивает разрешённые метаданные в `dsh-workspace-registry`, выбирает проект и модель L2. **Нет инструментов для файлов и терминала.** |
| **L2** | Проект, выбранный L1 | Планирует внутри проекта, подбирает модели L3, ставит шаги и может дополнительно сужать бюджет инструментов. L2 также может отправлять сообщения участникам той же группы Room с соответствующими правами. |
| **L3** | **Обязательно наследует** узел и область L2 | Выполняет шаги локально в пересечении прав роли L3, политики проекта и бюджета L2. |

## Сообщения и события завершения

`send_user` публикует видимый ответ; `send_parent` и `send_child` пробуждают адресата через очередь; `report_progress` / `get_progress` и `task_settled` управляют асинхронным прогрессом.

| Роль | Инструменты координации |
| --- | --- |
| L1 | `query_projects`, `list_models`, `dispatch_planner`, `agent_spawn`, `send_child`, `get_progress`, `send_user` |
| L2 | `list_models`, `dispatch_executor`, `send_parent`, `send_child`, `get_progress`, `report_progress`, `peer_send` (при наличии прав в Room) |
| L3 | `send_parent`, `report_progress` |
