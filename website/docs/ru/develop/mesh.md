# Mesh и сеансы

Prism объединяет **прозрачную по расположению маршрутизацию** (`dsh-mesh-node`) с **восстановлением Copy-on-Conflict**, благодаря чему оркестрация работает одинаково локально и удалённо и не зависает на блокировках записи.

## Прозрачность расположения

Каждый узел регистрирует Subagent Provider `prism-<nodeId>`. Координатор выдаёт одноразовый токен запуска и получает ID полноценного сеанса DSH на целевом узле. Поскольку **L1 выбирает область для L2**, а **L3 наследует область L2**, все файловые операции выполняются локально на узле-владельце.

## Подключение двух узлов

Поместите первый блок `mesh` на координаторе (`hub`), второй — на исполнителе (`worker`), задав общий секрет в `PRISM_WORKER_TOKEN` и зарегистрировав `atlas` с `nodeId: "worker"` с обеих сторон:

```json
{
  "nodeId": "hub",
  "peers": [{ "id": "worker", "url": "https://worker.example.org", "tokenEnv": "PRISM_WORKER_TOKEN" }]
}
```

```json
{
  "nodeId": "worker",
  "incoming": [{ "id": "hub", "tokenEnv": "PRISM_WORKER_TOKEN", "projects": ["atlas"] }]
}
```

Между машинами используйте HTTPS (HTTP на loopback допустим только для локальных тестов). У каждого узла свой `DSH_HOME`.

## Virtual Facade & Copy-on-Conflict

Снаружи уровни выглядят как лёгкие Subagent-интерфейсы, внутри — это **формальные сеансы DSH**. При конфликте блокировки записи раннер немедленно делает **Fork** наблюдаемой истории в новый сеанс, атомарно обновляет привязку и помечает старый сеанс для архивирования.

## Надёжность и удалённый просмотр

Сообщения, выбор модели, статусы и очереди хранятся в `conversations.sqlite`, а полные журналы — в сеансах DSH. Запросы `trace` идут по той же связи Mesh без захвата блокировки записи.
